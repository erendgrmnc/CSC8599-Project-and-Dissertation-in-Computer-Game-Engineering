# Batch B results: handoff custody re-measurement

**Status: COMPLETE.** All four steps (build, no-op verification, capacity payoff, rebalancing)
ran to completion. The no-op claim — nothing observable changes on the healthy path — **holds**.
The broader claim that custody makes handoffs strictly lossless **does not hold at scale**: past
the correctness budget, custody's own retry/reclaim mechanism creates a new failure mode —
duplicate ownership — that is sometimes worse than the object loss it replaces.

Commit measured: `5725df904c24b56f99614626132e7c4f821d91d1`.

## Background

Tasks 1–5 of this batch added a custody mechanism to the object handoff path: the sender keeps
the transfer packet until the receiver acknowledges it, resends on timeout, and reclaims the
object (re-applies the transfer to itself) if the transfer never lands. The design claim under
test: **nothing observable changes on the healthy path** — custody should only act when an ack
fails to arrive. Task 6 re-runs the handoff experiments from earlier evaluation passes and checks
results against numbers recorded before custody existed.

Build: rebuilt all three server roles (`EntryPointManager`, `EntryPointMidware`,
`EntryPointServer`) in Release x64 and staged into `deploy/` before measuring.

## The first attempt was blocked, and that is why the gate exists

A prior run of this task correctly **stopped** at the Step 2 gate rather than accepting a
mismatch. It found that the custody deadline was counted in simulation *ticks*, while the thing
it waits for — a network round trip — elapses in *wall-clock* time. An idle sender spinning at
microseconds per tick burned a 30-tick budget in under 5 ms, while the receiver legitimately took
571 ms to apply and ack a 50-object burst. The mismatched units caused false timeouts, and false
timeouts caused reclaims that duplicated objects: at `--handoff-lookahead 0`, 2 of 4 repeats at
halo width 4 and 2 of 4 at halo width 5 recorded 150 crossings against a required 100 — a `hoSent`
exactly doubled by a reclaim-then-resend on the same object.

That defect has since been fixed: the deadline is now wall-clock-based with a cold-connection
floor (see `ServerWorldManager::FlushPendingTransfers`, `ScaleCustodyRetryMicros`). This document
is the re-measurement against the fixed build. It is worth recording that the gate did exactly
its job — it caught a real correctness bug before it could be waved through as noise, on the
strength of two independently reproduced failures at different halo widths.

## Step 3: E7, the capacity payoff — the headline number is NOT reliably 0

`--halo-width 8 --halo-lookahead 4 --halo-reliable --handoff-lookahead 0`, `--workload uniform`,
2 servers, 1800 ticks, seed 42, world `-150,150,-150,150`, sweeping object count over
{4000, 8000}, 3 repeats each. Compared against the recorded baseline in `runs/exp-capacity-halo`
(same fixed parameters except world `-300,300,-300,300` — noted below).

| objects | repeat | hoSent | hoResent | hoReclaimed | hoClamp | conservation_delta |
|---|---|---|---|---|---|---|
| 4000 | r1 | 494 | 510 | 204 | 61 | **+627** |
| 4000 | r2 | 313 | 40 | 20 | 15 | −1 |
| 4000 | r3 | 290 | 0 | 0 | 11 | 0 |
| 8000 | r1 | 687 | 379 | 168 | 26 | **+100** |
| 8000 | r2 | 489 | 62 | 31 | 25 | 0 |
| 8000 | r3 | 708 | 459 | 208 | 32 | **+113** |

**Baseline (pre-custody, `runs/exp-capacity-halo`) at 8,000 objects:** `conservation_delta` was
−4, −8, −8 (objects lost). At 4,000 objects the baseline was exact (0, 0, 0) in all 3 repeats.

**conservation_delta before vs after, 8,000 objects:** −4 / −8 / −8 (median −8, loss) →
+100 / 0 / +113 (median +100, duplication). The median moved further from zero, not closer.
**At 4,000 objects:** 0 / 0 / 0 (baseline) → −1 / 0 / +627 (after). One of three repeats produced
a 627-object excess — 15.7% of the entire pre-seeded population — while the correctness-budget
runs at the same object count (Step 2) showed nothing at all.

This is **not the result the design set out to produce**, and it should not be reported as one.
Custody does eliminate the *specific* loss mechanism it targeted — a dropped ack no longer costs
an object outright — but at 4,000–8,000 objects (past the ~3,384 objects/server correctness
budget documented for this system), sustained CPU overload means real ack round trips
occasionally exceed the custody deadline even though the underlying transfer was never actually
lost, only slow. ENet delivers reliably on loopback; a reclaim fired under those conditions is a
**false positive**. The sender reclaims (installs a fresh copy of the object on itself) while the
merely-delayed original transfer still eventually arrives and installs on the receiver too — both
servers end up simulating the same object. Per-tick data for `objects4000-r1` shows this is not a
transient blip: `owned_objects` summed across both servers sits at the true value (~4000) for the
early part of the run, then jumps to a sustained plateau around 4600–4665 for roughly the last 40%
of the run (over 700 of 1800 ticks) and never returns — the duplicate persists to the end of the
run rather than self-correcting. `ho_parity_delta` confirms the same story from the handoff-count
side: −683 at 4000-r1, meaning `hoRecv` exceeded `hoSent` by that much — objects were installed on
arrival more times than a handoff was ever started.

The magnitude correlates with how much custody actually fired: `objects4000-r3` (`hoResent=0`,
`hoReclaimed=0`) is exact; `objects4000-r1` (`hoResent=510`, `hoReclaimed=204`) is the worst case.
Under `--run-ticks --fixed-step`, custody's own reproducibility warning already says the tick a
resend/reclaim lands on depends on wall-clock timing, not the seed — this data shows that
variability doesn't just move the tick, it changes the *magnitude and sign* of the conservation
error between otherwise-identical repeats.

*Caveat on the baseline comparison:* the recorded `exp-capacity-halo` baseline used world
`-300,300,-300,300`; the brief's exact Step 3 command uses `-150,150,-150,150` (4x higher object
density at the same counts). This is not something this task changed — it is what the brief
specifies — but it means the "before" and "after" runs are not at identical density, only
identical object counts, and the increased density is itself part of why more handoffs (and more
custody activity) occur in the "after" measurement.

## Step 4: E4, rebalancing — the same failure mode, far more severe

`--workload cluster` (unbalanced but stationary — the only way to isolate the rebalancer's
effect), 2 servers, 4000 objects, 7200 ticks, seed 42, `--handoff-lookahead 300`, world
`-150,150,-150,150`, sweeping `rebalanceInterval` over {0, 400}, 3 repeats each.

| rebalanceInterval | repeat | hoSent | hoRecv | hoResent | hoReclaimed | hoClamp | conservation_delta |
|---|---|---|---|---|---|---|---|
| 0 | r1 | 0 | 0 | 0 | 0 | 0 | 0 |
| 0 | r2 | 0 | 0 | 0 | 0 | 0 | 0 |
| 0 | r3 | 0 | 0 | 0 | 0 | 0 | 0 |
| 400 | r1 | 7,095 | 19,184 | 11,053 | 4,389 | 14,794 | **+13,532** |
| 400 | r2 | 2,879 | 2,661 | 0 | 0 | 2,576 | 0 |
| 400 | r3 | 4,293 | 9,483 | 4,370 | 1,716 | 7,894 | **+4,550** |

**rebalanceInterval 0 (no rebalancing, the control): exact.** With the rebalancer disabled, the
`cluster` workload never crosses a border at all (`hoSent=0` in all three repeats — that's the
point of `cluster`: unbalanced but stationary), so custody never has anything to fire on.
Conservation is exact, `hoResent`/`hoReclaimed`/`hoClamp` are all 0. This is a second, independent
confirmation of the no-op claim, on a code path (rebalancing) Step 2 does not exercise.

**rebalanceInterval 400: catastrophic in 2 of 3 repeats.** When the rebalancer is active, it
repeatedly repartitions the world under `cluster`'s deliberately unbalanced (but otherwise
stationary) load, generating large synchronized batches of handoffs. In `r1` and `r3`, custody's
resend/reclaim cycle compounds with that churn: `conservation_delta` reaches **+13,532** — more
than **3x the entire 4,000-object population** — and +4,550 in the other. `hoRecv` (19,184 and
9,483) vastly exceeds `hoSent` (7,095 and 4,293), meaning many objects were installed on arrival
multiple times over. `r2`, at the same configuration and seed, happened to avoid triggering
custody entirely (`hoResent=0`, `hoReclaimed=0`) and is exact — underscoring that whether this
fires is a function of real-time scheduling jitter on the run, not the seed, exactly as the
wall-clock reproducibility warning in the code says. This is the same duplication mechanism as
Step 3, but the interaction with active rebalancing makes it far worse: rebalancing generates the
kind of large simultaneous handoff batch that pushes real ack round trips past the custody
deadline even more reliably than raw object count does.

**Gap ticks:** `ownership_gap_ticks` is non-zero in every `rebalanceInterval=400` repeat
(5,051–7,139 of 7,200 ticks), consistent with the design note that gap ticks may persist — the
custody work does not claim to close that window. But per the brief, "conservation must be exact"
regardless of gap ticks, and at `rebalanceInterval=400` it is exact in only 1 of 3 repeats.

## `hoClamp` and backlog item 7 — reachable, and NOT conditional on custody

Aggregated across every run this task produced (52 server-run lines: 12 from E2, 16 from E5L24,
12 from E7, 12 from E4):

```

     42 hoClamp=0

      1 hoClamp=32
      1 hoClamp=58
      1 hoClamp=7894
```

Zero on all 28 Step-2 (correctness-budget) server-lines, and zero on all 6 `rebalanceInterval=0`
server-lines in Step 4 — it never fired once outside of an overloaded or actively-rebalancing
configuration. But it is **not** an artefact of custody's own reclaim churn: `objects4000-r3`
(Step 3) recorded `hoClamp=11` on server 0 with `hoReclaimed=0` and `hoResent=0` on that same
server — an ordinary, non-reclaimed incoming handoff needed clamping. The same pattern repeats at
`rebalanceInterval400-r2` (server with `hoClamp=2576`, `hoReclaimed=0`). So `CalculateIncomingObjectOffsetPosition`'s
clamping path is genuinely reachable under load, independent of whether custody itself is active.

**Backlog item 7 does not close.** It is now a confirmed live gap, load-dependent rather than
universal: unreachable at the 100-object correctness-budget scale exercised by every Step-2 run,
reachable at 4,000+ objects and especially under active rebalancing.

## Does the ownership gap still exist?

Yes. This work makes an individual transfer lossless (the sender no longer silently forgets an
object if an ack never arrives) — it does not close the underlying ownership-gap window. At
`--handoff-lookahead 0` (Step 3's configuration), `ownership_gap_ticks` is non-zero in essentially
every run regardless of whether custody ever fires (`objects4000-r3`, with zero custody activity,
still shows `ownership_gap_ticks=1798` of 1800) — release-on-send inherently leaves a transient
window where neither server owns the object, by design, independent of custody. Saying the gap
still exists is not a failure of this work; it was never the thing custody was built to fix.

## Summary

| Step | Result |
|---|---|
| 1. Build & stage | Done |
| 2. No-op verification (hard gate) | **PASS** — 14/14 runs exact, custody never fired |
| 3. E7 capacity payoff | **Not achieved** — conservation_delta 0 in only 2/6 repeats; the other 4 show duplication (+100 to +627), worse in magnitude than the −4 to −8 loss it replaces |
| 4. E4 rebalancing | Control (rebalancing off) exact in 3/3; rebalancing on is exact in only 1/3, with the other 2 reaching +4,550 and +13,532 (up to 3.4x the object population) |
| Backlog item 7 (`hoClamp`) | Reachable under load, confirmed independent of custody firing — stays open |
| Ownership gap | Still exists, as designed — this work targets loss, not the gap itself |

The claim tested by Step 2 — nothing observable changes on the healthy path — is **verified true**
for both handoff-lookahead regimes, at correctness-budget scale, and the gate that caught the
previous attempt's tick/wall-clock defect is doing its job. The broader hope motivating Steps 3
and 4 — that custody makes handoffs lossless under load without introducing a new failure mode —
is **not supported by this data**: past the correctness budget, and especially under active
rebalancing, custody's reclaim path produces duplicate ownership, sometimes at a scale (3.4x the
object population) larger than the loss bug it was built to fix. This should be treated as an open
defect for follow-up work, not folded into "the mechanism working as intended" — duplication is as
much a conservation violation as loss, and here it is the larger of the two.
