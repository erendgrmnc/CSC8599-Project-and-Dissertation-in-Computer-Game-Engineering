# Batch B results: handoff custody re-measurement

**Status: BLOCKED at the Step 2 no-op verification gate.** Steps 3 (E7 capacity payoff) and 4 (E4
rebalancing + full `hoClamp` survey) were not run. This document records what Step 2 measured and
why it stopped there; it is not the full evaluation the task plan intended to produce.

## Background

Tasks 1–5 of this batch added a custody mechanism to the object handoff path: the sender keeps
the transfer packet until the receiver acknowledges it, resends on timeout, and reclaims the
object if the transfer never lands. The design claim under test: **nothing observable changes on
the healthy path** — custody should only act when an ack fails to arrive. Task 6 re-runs the
handoff experiments from earlier evaluation passes and checks the results against numbers recorded
before custody existed. If any number differs, that claim is false and every measurement after it
would rest on an unverified assumption.

Build: rebuilt all three server roles (`EntryPointManager`, `EntryPointMidware`,
`EntryPointServer`) in Release x64 and staged into `deploy/` before measuring, since Task 5 changed
server code after the last staging pass.

## Step 2: no-op verification

Two experiments, each comparing recorded pre-custody baselines against the current build. Both use
`--workload headon` (every recorded collision is a border collision) at 100 objects, 2 servers,
1800 ticks, seed 42, world `-150,150,-150,150`.

### E2 — handoff lookahead 300 (scheduled release)

`--halo-lookahead 4 --halo-reliable --handoff-lookahead 300`, sweeping halo width over {0, 8},
3 repeats each.

| halo width | required crossings | measured crossings (all 3 repeats) | required contacts | measured contacts (all 3 repeats) |
|---|---|---|---|---|
| 0 | 100 | 100, 100, 100 | 76,600 | 76,600, 76,600, 76,600 |
| 8 | 0 | 0, 0, 0 | 82,390 | 82,390, 82,390, 82,390 |

**Result: PASS.** Every repeat matches the recorded baseline exactly. `hoResent` and
`hoReclaimed` are 0 on every server in every run — custody never activated. Under
`--handoff-lookahead 300`, the no-op claim holds.

### E5, L=24 — handoff lookahead 0 (release on send)

`--halo-lookahead 24 --halo-reliable --handoff-lookahead 0`, sweeping halo width over
{4, 5, 6, 7}, 2 repeats each. (L=24 is the halo-lookahead value at which the earlier evaluation
located the cross-border-collision "knee" at halo width 6 — the point below which contacts are
lost to a too-narrow halo.)

| halo width | required crossings | measured crossings (repeat 1, repeat 2) | measured contacts (repeat 1, repeat 2) |
|---|---|---|---|
| 4 | 100 | 100, **150** | 81,350, 78,700 |
| 5 | 100 | 100, **150** | 79,100, 78,600 |
| 6 | 0 | 0, 0 | 109,170, 109,170 |
| 7 | 0 | 0, 0 | 109,170, 109,170 |

**Result: FAIL for halo widths 4 and 5.** Repeat 1 of each matches the required 100 crossings;
repeat 2 of each does not — 150 instead of 100, a 50% inflation, reproduced independently at two
different halo widths. Widths 6 and 7 pass (0 crossings, confirming the knee is still at 6).

**Diagnosis.** The `@@FINAL` per-server counters show the mechanism directly. In every failing
repeat, one server's `hoReclaimed` is non-zero (50) and that same server's `hoSent` is exactly
double what it is in the passing repeat (100 vs 50) — i.e. an object that had its custody
reclaimed after an unacknowledged send is later sent again as an independent handoff, counted a
second time. No fault was injected (`--handoff-delay-ticks` was 0, its default). The retry timeout
uses its default (`--handoff-retry-ticks` 30, `--handoff-max-attempts` 3), which was apparently
sized for a scheduled-release regime: at `--handoff-lookahead 0` (release on send), real ENet
delivery jitter is occasionally enough — even in tick-paced "reproducible" mode — to cross that
30-tick deadline and trigger a reclaim that a genuinely healthy send/ack round trip should not
need. This happened in 2 of 4 repeats at L=4 and 2 of 4 at L=5.

**Conclusion:** the "custody is invisible on the healthy path" claim is **true for
`--handoff-lookahead 300`** (scheduled release: E2 passed 6/6 repeats, zero custody activity) and
**false for `--handoff-lookahead 0`** (release on send: custody activates on ordinary network
timing, not just injected faults, in roughly half of repeated runs). This is a real behavioural
change under a supported configuration, not measurement noise — it reproduced identically across
two independent halo widths.

## Steps 3 and 4: not run

Per the task instructions, a Step 2 mismatch is a stop condition: "the claim that custody is
invisible on the healthy path is false and the design needs revisiting before any further
measurement." E7 (capacity payoff at 4,000/8,000 objects) and E4 (rebalancing with `hoClamp`
survey) were not executed. There is therefore:

- **No E7 conservation-delta figure to report, before or after.** The comparison this batch
  exists to produce (baseline `conservation_delta` of −4 to −8 at 8,000 objects, custody's claimed
  fix to 0) is deferred until the lookahead-0 behaviour above is understood or the retry timing is
  retuned.
- **No `hoResent` / `hoReclaimed` totals across the full run set** — only the Step 2 runs exist.
  Summed across `custody-E2` and `custody-E5L24`: `hoResent` totals 700 (all in E5L24; E2 is 0),
  `hoReclaimed` totals 100 (E5L24 only, the two failing repeats' 50 + 50).
- **No E4 result.**
- **`hoClamp` verdict on backlog item 7 is incomplete.** Across all 28 server-run lines produced by
  Step 2 (`custody-E2`: 12, `custody-E5L24`: 16), `hoClamp` is 0 everywhere:

  ```
  $ grep -ho "hoClamp=[0-9]*" runs/exp-custody-*/*/mid.log | sort | uniq -c
       28 hoClamp=0
  ```

  This is consistent with backlog item 7 being unreachable, but Step 3 and Step 4 (which add 6 more
  runs at up to 8,000 objects and 6 runs at 7,200 ticks under a rebalancing workload — the
  conditions most likely to exercise a clamp) never ran. Item 7 stays **open**, not closed, until
  those runs exist.

## Does the ownership gap still exist?

Not measured in this pass — E7 (the experiment that quantifies it via `conservation_delta`) did
not run. Nothing in Step 2 bears on this question either way; the batch's design intent stands as
documented elsewhere: custody makes transfers lossless (retried/reclaimed rather than dropped), it
does not eliminate the underlying window where an object is briefly unowned during a handoff. That
remains the expectation pending Step 3.

## Bottom line

The no-op verification gate this task exists to run caught a real issue: custody is not invisible
on the healthy path when `--handoff-lookahead 0`. The retry-timeout default appears tuned for
`--handoff-lookahead 300` and is too tight for release-on-send operation under ordinary network
jitter. Recommendation before any further measurement: either widen `--handoff-retry-ticks` for
lookahead-0 operation, or explicitly scope the no-op claim to lookahead > 0 and treat
lookahead-0 custody activity as expected background behaviour rather than a fault indicator. This
task should be re-run (Steps 2–5) once that decision is made and, if code changes, once the build
is re-staged.
