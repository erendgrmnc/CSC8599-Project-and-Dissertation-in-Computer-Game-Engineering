## Claim under test

The broadphase was already shown to be linear in object count (`docs/superpowers/specs/2026-08-18-scale-ceiling.md`,
exponent 1.07), which replaced an O(n²) inner loop with a uniform grid. But a grid's constant factor
is set by occupancy — how many objects land in the same cell — not by count alone, and count and
occupancy are the same thing only when the world grows with the objects. A real game world doesn't do
that: players cluster. This experiment holds the world bounds **fixed** at 300×300 and grows the
object count from 500 to 8,000, which raises objects-per-cell instead of holding it constant. The
question: does per-tick physics cost stay linear as density rises, or does it degrade — and if it
degrades, where's the knee, since that number bounds how much clustering one region can absorb before
the partition has to move.

## Cell size: confirmed from source, and it is not what the brief assumed

`CSC8503CoreClasses/PhysicsSystem.cpp:651`:

```cpp
mBroadphaseGrid.cellSize = std::max(1.0f, maxExtent * 4.0f);
```

confirmed verbatim — the formula itself matches the brief. `maxExtent` (`PhysicsSystem.cpp:644-650`) is
the largest `max(halfSize.x, halfSize.z)` over every object in `mDynamicObjectList` that has physics,
recomputed every tick from `GetBroadphaseAABB`.

The brief assumed the workload's objects are "unit cubes" giving `maxExtent = 1.0` and cell size 4.0.
Reading the object-construction code (`DistributedGameServer/ServerWorldManager.cpp`) shows this is
wrong:

- `AddCubeToWorld` (`ServerWorldManager.cpp:1911`) builds `AABBVolume(Vector3(0.5, 0.5, 0.5))` — a
  cube with **half**-extent 0.5, i.e. a genuinely unit (1×1×1) cube, not a half-extent-1 (2×2×2) one.
- `AddSphereToWorld` (`ServerWorldManager.cpp:1937`) builds a sphere of radius 0.5 — same half-extent.
- `CreateObjectGrid` (`ServerWorldManager.cpp:1705-1739`), which is what `--workload uniform`'s pre-seed
  actually calls, splits objects 50/50 between these two archetypes by a deterministic hash. Both have
  half-extent 0.5, so `maxExtent = 0.5` regardless of the split.
- The one object type with a larger half-extent, the radius-5 controllable player sphere built by
  `AddDistributedControllableObject` (`ServerWorldManager.cpp:1887`), is **never called** — its only
  call sites (`ServerWorldManager.cpp:130,145`) sit inside a block commented out in its entirety
  (confirmed by `grep -n "AddDistributedControllableObject" -r .`, which returns only the declaration,
  the definition, and those two commented call sites). No player avatar exists in this world.
- The floor (`AddFloorWorld`, half-extent 500×1×500) is on the static collision layer and is inserted
  into `mStaticTree`, not `mDynamicObjectList` (`PhysicsSystem.cpp:500-513` routes any
  `STATIC_COLLISION_LAYERS` object to the static tree and returns before it reaches the dynamic list),
  so it never contributes to `maxExtent`.

So for this workload, every tick: `maxExtent = 0.5`, giving

```
cellSize = max(1.0, 0.5 * 4.0) = max(1.0, 2.0) = 2.0
```

not 4.0. Over a 300×300 world that is **150 cells per axis, 22,500 cells total** — four times the
brief's worked table (75/axis, 5,625 cells). The objects-per-cell column below uses the corrected
22,500, not the brief's 5,625.

## Fitted exponent

Log-log least-squares fit of p95 against object count (which is proportional to density here, since
the cell count is fixed across the whole sweep):

- **Full range (500–8,000): exponent = 0.96, R² = 0.983.**
- **1,000–8,000 only: exponent = 1.09, R² = 0.998.**

The full-range fit is pulled down by the 500→1,000 step, whose local exponent is only 0.52 (p95 rises
1.44x on a 2x object increase) — well below linear, plausibly a fixed per-tick floor (metrics/loop
overhead) that matters proportionally more when the physics work itself is still small. From 1,000
objects up, the fit is consistently near-1.1 (excellent R² = 0.998), and the four consecutive
doubling steps tell the same story directly:

| step | p95 ratio (2x objects) | local exponent |
|---|---:|---:|
| 500 → 1,000 | 1.44x | 0.52 |
| 1,000 → 2,000 | 1.94x | 0.96 |
| 2,000 → 4,000 | 2.24x | 1.17 |
| 4,000 → 8,000 | 2.16x | 1.11 |

p50 tells a consistent story (full-range exponent 1.00, 1,000–8,000 exponent 1.07); p99 is noisier
(0.93 / 1.00) as expected from a percentile further into the tail with only n=3 repeats per point.

## Verdict: mildly super-linear from ~2,000 objects up, no cliff, no sharp knee in range

**Cost does not stay purely linear as density rises, and it does not degrade catastrophically either.**
From roughly 2,000 objects (0.089/cell) onward, each doubling of density costs about 10–17% more than
a linear model predicts, and this holds steadily through the highest density tested (8,000 objects,
0.356/cell, p95 = 14.81 ms) — there is no sudden jump, no point where the curve bends sharply upward
relative to its own recent trend. The 500→1,000 step is the outlier, and it runs *below* linear, not
above — consistent with fixed overhead, not with a broadphase problem.

**There is no knee inside the tested range (0.022–0.356 objects/cell).** The mild super-linearity is a
steady drift present from ~0.089/cell onward, not a threshold effect the data crosses partway through.
The honest statement is: within 500–8,000 objects on a fixed 300×300 world, cost tracks close to
linear (exponent ≈1.0–1.1 depending on the range fitted), trending mildly super-linear as density
climbs, with no evidence of a breakdown point up to 8,000 objects — the highest density tested (0.356
objects/cell, i.e. roughly one object per 2.8 cells) behaves in line with the trend set by the points
below it, not as an anomaly.

**What this means for per-server capacity.** Planning per-region capacity on a pure O(n) assumption
would under-predict cost by roughly 10-17% per density doubling once occupancy passes ~0.09/cell — a
load balancer using a linear cost model to decide when to move a border will be consistently a little
optimistic at higher density, not badly wrong. Since no knee was found up to 0.356 objects/cell, this
experiment cannot bound how much clustering a region can absorb before the cost model breaks down
outright; it can only say that up to that density, the degradation is a steady ~10% drift, not a cliff.
Answering "where does it actually break" would need points denser than 8,000 objects on this world (or
a smaller world at the same object counts) — out of scope here, but the natural next sweep.

## Limitations

- Single server, single workload (`uniform`), single seed (42), n=3 repeats per point — sufficient to
  see the trend and its steadiness, not enough to tighten the exponent's confidence interval much
  further.
- p99 at n=3 is noisy; it is reported for context but p95 is the figure this document treats as
  authoritative, per the task's brief.
- The 500→1,000 sub-linear step is plausible but not confirmed to be fixed-overhead-driven; that would
  need a lower-object-count point (e.g. 100, 200) to isolate the floor from the trend, which was not in
  the requested sweep.
