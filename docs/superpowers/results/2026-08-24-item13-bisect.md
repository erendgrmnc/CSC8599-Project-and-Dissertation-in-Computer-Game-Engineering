# Item 13 bisect — the snapshot-throughput change does not exist

**Date:** 2026-08-24
**Range:** `02e306b..2060f55` (61 commits, 27 touching engine/server code)
**Outcome:** item 13 closes. There is no build difference. The 3.6x is a **measurement-harness
artefact**: the client that the servers were sending snapshots to was alive for 5 seconds of a
20-second run before `e413ab0`, and for the whole run after it.

This also **retracts** `2026-08-24-item13-counterfactual.md`, written earlier the same day, which
concluded the difference was real and build-scoped.

---

## Signal

1 server, `--halo-width 0`, `--interest-radius 0`, 4,000 objects, 20 s realtime, `uniform`,
2 repeats. The cheapest configuration showing the effect at full strength: no halo band, no peer
links, no handoffs, and `snapSupp` = 0 so nothing is filtered.

`snapSent` is always an exact multiple of 4,000 — the whole object set — so the natural unit is
**ticks per snapshot event**, which is what the tables below report. Every event sends all 4,000
objects on *both* sides of the change; only the event *rate* differs. That was the first clue that
this was not about snapshot content.

The window's other change is `tools/measure.ps1`.

## Cause

`e413ab0 fix(measure): client must outlive the servers when it sends no commands`

```powershell
- $clientSeconds = [Math]::Max(5, $serverRunSeconds - 15)
+ $clientSeconds = if ($clientDrivesCommands) { [Math]::Max(5, $serverRunSeconds - 15) }
+                  elseif ($Ticks -gt 0)      { [Math]::Max(120, $Ticks / 8) }
+                  else                       { $Seconds + 45 }
```

On a 20-second realtime run the old rule gives the client `max(5, 20-15)` = **5 seconds**. The new
rule gives it `20 + 45` = **65**.

`DistributedGameServerManager::BroadcastSnapshot` counts `mSnapshotsSent += targets.size()`, and
`targets` is the connected clients. With the client gone, there are no targets and the counter
simply stops advancing. The servers keep running and keep stepping the world for the remaining
15 seconds; nothing is recorded because nothing is being sent to anyone.

So the quantity that changed by 3.6x was never throughput. It was **how much of the run had a
client attached to it**.

`e413ab0` was made for an unrelated reason — a client dying mid-run left the servers broadcasting
reliable spawn packets at a peer that had stopped acknowledging, blocking their loop for 8.0 s and
then 26.0 s. Its effect on snapshot counts went unnoticed, which is unsurprising: a counter that
stops incrementing looks like low throughput, not like a missing client.

## Proof, with the binary held fixed

The decisive control changes only the client lifetime. Same `dd63915` build, same configuration,
`$clientSeconds` forced to 5:

| `dd63915` binary | snapSent | ticks/event |
|---|---|---|
| client 65 s (as shipped) | 2,516,000 / 2,868,000 | **2.00 , 2.00** |
| client 5 s (pre-`e413ab0` rule) | 948,000 / 940,000 | **6.04 , 6.20** |

This reproduces the entire OLD/NEW split — the whole of item 13 — with **no code difference at
all**. 20/5 = 4.0 against an observed ratio of ~3.1, the shortfall being the client's connect
handshake and the servers' own start-up spread.

## What this means for E8

**The published E8 measurement (`02e306b`, 2026-08-20) ran with the client attached for roughly the
first quarter of each run.** `e413ab0` landed 2026-08-21. Phase A's re-measurement (`2060f55`) has
the client attached throughout.

- **Absolute byte and snapshot rates from the published run are measured over a truncated window**
  and should not be quoted as run rates.
- **Per-radius comparisons within either session remain internally valid** — all four radii in a
  given sweep shared one client lifetime — so E8's reduction fractions are not invalidated, only
  its absolute figures.
- **The two sessions are not comparable in absolute terms.** That is exactly what item 13 observed;
  it now has a cause.
- The published build's apparent instability (130% within-radius spread, "servers failing to
  accumulate ticks") is explained by the same thing: when the count depends on a client that dies
  a few seconds in, it depends on precisely when it died.
- The counterfactual "the published build would have failed at radius 100" is computed on numbers
  gathered over a quarter-length window. It does not bound the current build's verdict, and the
  build-scoping hedge on E8 does not rest on a real build difference.

## Method failure worth recording

Three of the ten probes had to be discarded and re-run. Probe blocks that timed out were moved to
the background by the harness and **kept running**; re-running the same probe in the foreground put
two experiments on the machine at once, each killing the other's processes, and — because snapshots
are counted per object *per client* — a second experiment's client inflates `snapSent` directly.
One contaminated probe reported 2,336,000 where the run on disk held 708,000, and one directory was
silently overwritten by a late background task measuring a **different commit's build**.

The corrective, applied from probe 7 onward: never re-issue a probe that may still be running, wait
for completion explicitly, verify no `EntryPoint` process survives, and read results **from the run
directory** rather than from the launching script's stdout. Probes 1, 2, 7, 8, 9, 10 and the control
above were all collected that way; the discarded ones are not in this table.

The deeper mistake was the same one that produced the retracted counterfactual: when comparing two
harness versions I diffed the `-ArgumentList` lines and not the variables feeding them. Both of
today's wrong conclusions came from checking a call site instead of its inputs.
