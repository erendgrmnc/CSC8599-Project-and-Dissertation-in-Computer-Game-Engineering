## Claim under test

Every per-server capacity figure this project has published — ~6,000 objects serial, ~10,000 with
`--physics-threads` — was measured with `--halo-width 0`, i.e. cross-border collision **disabled**.
That is not the configuration this work advocates:
`docs/superpowers/specs/2026-08-18-scale-ceiling.md` §4 item 2 names this gap explicitly ("per-server
capacity curve in Release, with the halo on, to find the real object budget per server rather than
the ~6,000 measured with it off"), and §5.3 is the figure being corrected here:

> Per server, at 120 Hz on this hardware: ~6,000 objects serial, and the 1.65x gives roughly 10,000
> objects per server with workers.

This experiment finds the real per-server object budget with `--halo-width 8` (band publication +
read-only shadow collision) enabled, against a matched halo-off baseline at the same points, so any
difference is attributable to the halo alone and not to a different world, workload, or server count.

## Scope change from the brief (stated up front)

The brief specified `-Values "1000,2000,4000,8000,12000"`. **The 12,000-object point was dropped for
time** under the deadline that governed this task; the sweep actually run was
`-Values "1000,2000,4000,8000"`, 3 repeats, both configurations — 24 runs instead of 30. Consequence:
the halo-off crossing (below) falls just outside the swept range and is **extrapolated from the last
two points, not bracketed from above** by a measured 12,000-object point. The halo-on crossing
happens to fall inside the swept range regardless (between 4,000 and 8,000), so it is a true
interpolation. This is stated as a limitation, not hidden in the numbers.

The 1,000-object point is negative (halo on is *faster*), which is noise at n=3, not a real effect —
the halo does no work worth measuring when nothing is near a border. From 2,000 objects up the cost
is real and grows with load, both in absolute ms and as a fraction of the halo-off baseline (15.6% →
19.5% → 37.9%): the halo gets proportionally more expensive as the system gets busier, not just
additively more expensive. That is the shape a reader should take away — flat overhead would mean a
constant Δ; instead Δ tracks total load.

## Budget crossing: tick budget is 8.33 ms at 120 Hz

**Halo ON** — busiest p95 crosses 8.33 ms between the 4,000 and 8,000 point (**true interpolation,
bracketed by measured data on both sides**):

```
x = 4000 + (8.33 - 4.0354) / (10.2438 - 4.0354) * (8000 - 4000)
  = 4000 + 0.6918 * 4000
  ≈ 6,767 total objects  →  ≈ 3,384 objects per server
```

**Halo OFF** — busiest p95 does **not** cross 8.33 ms within the swept range; the 8,000-object point
(7.4262 ms) is still under budget. Crossing is **extrapolated** from the trend of the last two swept
points (4,000 → 8,000), which is where the dropped 12,000 point would otherwise have bracketed it
from above:

```
x = 8000 + (8.33 - 7.4262) / (7.4262 - 3.3780) * (8000 - 4000)
  = 8000 + 0.2233 * 4000
  ≈ 8,893 total objects (EXTRAPOLATED, not bracketed)  →  ≈ 4,447 objects per server
```

**Cost of the halo at the halo-on crossing point** (6,767 total objects): interpolating the halo-off
curve to that same object count gives ≈6.179 ms, vs. the 8.33 ms budget the halo-on curve has just
hit — a **2.15 ms gap, 25.8% of the 8.33 ms budget**, paid at the point where the halo-on system is
already saturated. In other words: at the load where cross-border collision first blows the tick
budget, disabling it would have bought back roughly a quarter of the budget.

## Corrected per-server budget

| configuration | crossing (total, 2 servers) | crossing (per server) | how obtained |
|---|---:|---:|---|
| `--halo-width 0` (what every prior figure used) | ≈8,893 | ≈4,447 | extrapolated past the swept range |
| `--halo-width 8` (what the work advocates) | ≈6,767 | ≈3,384 | interpolated, bracketed by measured data |

Both figures are markedly below the previously published ~6,000 (serial, halo off) and ~10,000
(threaded, halo off) from `docs/superpowers/specs/2026-08-18-scale-ceiling.md` §5.3. Two things
change between those figures and this experiment, and both push the number down, not up:

1. **The halo itself** costs 25.8% of budget at its own crossing point (above) — this is the
   headline number this experiment was run to produce.
2. **Even with the halo off**, this experiment's per-server figure (~4,447, extrapolated) sits below
   the previously published ~6,000. That prior figure came from a genuinely single-server,
   non-partitioned measurement; this one is a real 2-server distributed run (border checks, handoff
   bookkeeping, cross-server networking) even with `--halo-width 0`. That distributed overhead, not
   present in a single-server run, plausibly accounts for the gap — see the cross-check below.

**Bottom line: the real, corrected per-server object budget at 120 Hz with cross-border collision
enabled — the configuration this work actually advocates — is approximately 3,400 objects per
server, not ~6,000 and not ~10,000.** Those higher, previously published figures describe a
configuration (`--halo-width 0`) this project does not recommend running.

## Cross-check against the sibling density experiment (E6)

E6 (`docs/superpowers/results/2026-08-19-E6-density.md`), 1 server, halo off, world ±150, measured
**4,000 objects → p95 6.8508 ms**. This experiment's closest comparable point is the halo-off
8,000-total point, ~4,000 objects on the busier of 2 servers → **p95 7.4262 ms**.

The two numbers are in the same neighbourhood (both single-digit ms, same order of magnitude,
~8.4% apart) but do not match closely, and the direction is the opposite of what raw density would
predict: this experiment's world is 4x the area of E6's for the same swept object count, and (per
the halo/broadphase design in `CSC8503CoreClasses/PhysicsSystem.cpp:651` — the grid is a sparse hash
map keyed by occupied cell, not a fixed dense array sized to world extent) a larger, no-denser spread
should if anything be *cheaper* per tick, not more expensive. The plausible explanation is that this
experiment is a genuine 2-server **distributed** run even with the halo off — per-tick border
ownership checks (`IsObjectInBorder`/`OwningServerFor`), handoff state-machine bookkeeping for
objects crossing the shared seam, and the general two-process setup — none of which E6's single,
unpartitioned server pays. `physics_ms` is scoped to `PhysicsSystem::Update` (broadphase + integrate
+ resolve) so most of that overhead shouldn't land inside the metric at all, which is why the gap is
~8% rather than dominant; it is still worth flagging as a discrepancy rather than silently accepting
the two figures as interchangeable. **Verdict: same order of magnitude, corroborating that neither
experiment is off by a gross factor, but not an exact match — attributed to distributed-vs-single-server
overhead, not investigated further here (out of scope for this task).**

## Concerns / caveats

- **12,000-object point dropped for time.** The halo-off crossing (≈8,893 total) is extrapolated
  past the last swept point (8,000), not bracketed from above by measured data. The halo-on crossing
  (≈6,767) is unaffected — it falls inside the swept range regardless.
- n=3 repeats per point, matching the rest of this project's convention; sufficient to see the trend
  (the 1,000-object Δ sign flip is visibly noise at this n) but not to tighten a confidence interval
  on the exact crossing objects count.
- Linear interpolation/extrapolation between adjacent swept points was used throughout, for both
  configurations, for consistency — not a fitted curve. E6 found tick cost mildly super-linear
  (exponent ~1.09) in the same object range; a super-linear fit would place both crossings slightly
  *earlier* (fewer objects) than the linear estimates above, so if anything these figures are mildly
  conservative (optimistic about capacity), not the reverse.
- `analyse.py` invariant failures (`ownership_gap_ticks`, and `conservation_delta`/`ho_parity_delta`
  at 8,000 objects) appear on nearly every run in both configurations. This is the pre-existing,
  already-documented handoff-ack stub gap (see `CLAUDE.md`), unrelated to the halo and unrelated to
  the timing numbers reported here (`physics_ms` does not include handoff-ack logic). Not
  investigated further — out of scope for a capacity measurement.
